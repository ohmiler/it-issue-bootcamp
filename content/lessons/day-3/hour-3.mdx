# Form State and Validation

## Day 3 - ชั่วโมงที่ 3: ทำให้ Form โต้ตอบกับผู้ใช้

### เป้าหมายของชั่วโมงนี้

หลังจบชั่วโมงนี้ นักศึกษาจะสามารถ:

1. แยกความต่างระหว่าง Server Component และ Client Component ได้
2. ใช้ `"use client"` เมื่อต้องใช้ State หรือ Event Handler
3. ใช้ `useState` เก็บรายการปัญหาชั่วคราวใน Browser
4. อ่านค่าจาก Form ด้วย `FormData`
5. ตรวจข้อมูลและแสดงข้อความ Error
6. เพิ่มปัญหาใหม่เข้า Mock List โดยยังไม่ใช้ Database
7. อธิบายได้ว่าทำไม Frontend Validation ยังไม่เพียงพอสำหรับความปลอดภัย

### ไฟล์ที่ใช้

```text
components/IssueBoard.tsx  ← สร้างใหม่
components/IssueForm.tsx   ← แก้ไข
app/page.tsx               ← แก้ไข
```

ไฟล์ที่นำมาใช้ต่อโดยไม่แก้โครงสร้างหลัก:

```text
components/IssueList.tsx
types/issue.ts
data/issue.ts
```

## Slide 1: จาก Form ไปสู่รายการใหม่

ตอนนี้ Form และ List มีหน้าตาพร้อมแล้ว แต่การกดส่งยังไม่เพิ่มรายการ

ชั่วโมงนี้เราจะต่อการทำงาน: อ่าน Form → ตรวจข้อมูล → เพิ่มรายการใน State → แสดง List ใหม่

`IssueBoard` จะเก็บรายการให้ Form และ List ใช้ร่วมกัน โดยเริ่มจาก Mock Data เดิม

ข้อมูลใหม่ยังอยู่ชั่วคราวในหน้า Home และยังไม่บันทึกลง Database

---

## Slide 2: เลือกส่วนที่ต้องเป็น Client Component

หน้าและ Layout เป็น **Server Component** โดยค่าเริ่มต้น ส่วนที่ต้องใช้ State หรือรับ Event ต้องอยู่ใน **Client Component**

| ไฟล์ | หน้าที่ในชั่วโมงนี้ |
|---|---|
| `app/page.tsx` | Server: ส่ง Mock Data เริ่มต้น |
| `IssueBoard.tsx` | Client: เก็บรายการที่เปลี่ยนได้ |
| `IssueForm.tsx` | Client: รับ Submit และแสดง Error |

Client Component ยังอาจถูก Render เป็น HTML บน Server ตอนเปิดหน้า จึงใช้ Browser API ใน Event Handler ที่ทำงานใน Browser ไม่เรียกตอน Render โดยตรง

---

## Slide 3: ขอบเขตของ use client

ตัวอย่างอธิบาย ยังไม่ต้องแก้ไฟล์:

```tsx
"use client";

import { useState } from "react";
```

`"use client"` อยู่ก่อน Import เพื่อกำหนดจุดเริ่มต้นของฝั่ง Client และไฟล์ที่ Import ต่อจากจุดนี้จะอยู่ใน Client Bundle ด้วย

`IssueForm` ถูกใช้ทั้งจาก `IssueBoard` และหน้า `/issues/new` จึงจะประกาศขอบเขต Client ที่ไฟล์ Form ด้วย

`useState` เก็บข้อมูลระหว่างการ Render และให้ Function สำหรับเปลี่ยนข้อมูลแล้วแสดง UI ใหม่

---

## Slide 4: State ของรายการควรอยู่ที่ไหน

`IssueForm` สร้างรายการ ส่วน `IssueList` แสดงรายการ จึงให้ Parent ชื่อ `IssueBoard` เก็บข้อมูลร่วมกัน

- `items` คือรายการปัจจุบัน
- `initialIssues` คือรายการเริ่มต้นที่หน้า Home ส่งมา
- Form ส่งรายการใหม่กลับไปให้ Board
- Board อัปเดต State แล้วส่ง `items` ให้ List

วิธีนี้เรียกว่า **Lifting State Up** คือย้าย State ไปไว้ที่ Parent ที่ Component ลูกใช้ร่วมกัน

Error ของ Form ใช้เฉพาะใน Form จึงเก็บ State แยกไว้ใน `IssueForm`

## Slide 12: อ่านค่าผ่านชื่อ Field

<LessonCallout type="action">เพิ่ม Function ใหม่ `getIssueInput` ใน `components/IssueForm.tsx` ต่อจาก `NewIssueInput` และก่อน `IssueForm`</LessonCallout>

<CodeChange language="tsx" addedLines="1,2,4,5,6,7,8,9,10">

```tsx
function getIssueInput(form: HTMLFormElement): NewIssueInput {
  const formData = new FormData(form);

  return {
    reporterName: String(formData.get("reporterName") ?? "").trim(),
    reporterEmail: String(formData.get("reporterEmail") ?? "").trim(),
    title: String(formData.get("title") ?? "").trim(),
    description: String(formData.get("description") ?? "").trim(),
  };
}
```

</CodeChange>

`formData.get()` ใช้ชื่อให้ตรงกับ `name` ของช่องกรอก; `?? ""` ใช้ค่าว่างเมื่อไม่พบข้อมูล

`String()` แปลงค่าเป็นข้อความ และ `.trim()` ตัดช่องว่างหัวท้าย ก่อนนำไปตรวจ

## Slide 13: กำหนดเงื่อนไขตรวจข้อมูล

<LessonCallout type="action">เพิ่ม Function ใหม่ `validateIssueInput` ใน `components/IssueForm.tsx` ต่อจาก `getIssueInput` และก่อน `IssueForm`</LessonCallout>

<CodeChange language="tsx" addedLines="1,2,3,4,5,6,7,8">

```tsx
function validateIssueInput(input: NewIssueInput): string[] {
  const errors: string[] = [];
  if (input.reporterName.length < 2) errors.push("ชื่อผู้แจ้งต้องมีอย่างน้อย 2 ตัวอักษร");
  if (!input.reporterEmail.includes("@")) errors.push("กรุณาตรวจสอบอีเมลผู้แจ้ง");
  if (input.title.length < 5) errors.push("หัวข้อปัญหาต้องมีอย่างน้อย 5 ตัวอักษร");
  if (input.description.length < 10) errors.push("รายละเอียดต้องมีอย่างน้อย 10 ตัวอักษร");
  return errors;
}
```

</CodeChange>

แต่ละ `if` เพิ่มข้อความที่ไม่ผ่านเงื่อนไขลง Array; ถ้าผ่านทุกข้อจะได้ `[]`

การหา `@` เป็นเพียงการตรวจเบื้องต้น และ Form ยังมี `type="email"` ของ Browser ช่วยตรวจอยู่

## Slide 14: เก็บ Error ใน State

<LessonCallout type="action">แก้บางส่วนใน `components/IssueForm.tsx`: เพิ่ม State เป็นบรรทัดแรกภายใน `IssueForm` แล้วแทน Handler ตามด้านล่าง</LessonCallout>

<CodeChange language="tsx" addedLines="1">

```tsx
const [errors, setErrors] = useState<string[]>([]);
```

</CodeChange>

แทน `handleSubmit` เดิมด้วย:

<CodeChange language="tsx" addedLines="3,4,5,6">

```tsx
function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
  event.preventDefault();
  const input = getIssueInput(event.currentTarget);
  const validationErrors = validateIssueInput(input);
  setErrors(validationErrors);
  if (validationErrors.length > 0) return;
}
```

</CodeChange>

`event.currentTarget` คือ Form ที่ Submit; `setErrors` เปลี่ยน State และ `return` หยุดเมื่อข้อมูลยังผิด

## Slide 16: ลอง Error สองรูปแบบ

<LessonCallout type="action">เปิดหน้า Home `/` แล้วทดสอบ Form ตามลำดับ โดยคง `required` และ `type="email"` ไว้</LessonCallout>

1. เว้นช่องว่างแล้วส่ง: Browser จะเตือนจาก `required` ก่อนเรียก Handler
2. กรอกชื่อ `A`, อีเมล `a@example.com`, หัวข้อ `abc`, รายละเอียด `short` แล้วส่ง
3. ควรเห็นกล่อง Error สามข้อจาก State และข้อมูลใน Form ยังอยู่
4. แก้ชื่อเป็น `An`, หัวข้อ `เครื่องพิมพ์เสีย`, รายละเอียด `เครื่องพิมพ์ชั้นสองพิมพ์งานไม่ได้` แล้วส่ง
5. กล่อง Error ควรหาย แต่ยังไม่เพิ่มรายการ เพราะยังไม่ได้เชื่อม Callback

Error ของ Browser และกล่องที่เราเขียนเองเป็นการตรวจคนละขั้น

## Slide 19: ส่งข้อมูลเมื่อผ่าน Validation

<LessonCallout type="action">เพิ่มโค้ดใหม่ใน `components/IssueForm.tsx`: ภายใน `handleSubmit` วางต่อจาก `if (validationErrors.length > 0) return;` ก่อนวงเล็บปิดของ Handler</LessonCallout>

## Slide 20: ให้ Board เพิ่มรายการใน State

## Slide 21: ทดสอบเพิ่มรายการที่ Home

<LessonCallout type="action">เปิดหน้า Home `/` แล้วทดสอบเพิ่มสองรายการและ Refresh เพื่อตรวจการทำงานของ State</LessonCallout>

1. เปิด `/` กรอกข้อมูลให้ผ่านทุกเงื่อนไข แล้วกดส่ง
2. Row ใหม่ต้องอยู่บนสุด มีสถานะ `OPEN` และจำนวนรายการเพิ่มหนึ่ง
3. Form ต้องว่าง และกล่อง Error เดิมหายไป
4. เพิ่มอีกหนึ่งรายการ แล้วตรวจว่ารายการก่อนหน้ายังอยู่
5. Refresh หน้า: รายการที่เพิ่มหาย และกลับมาเป็น Mock Data เดิม

State ช่วยให้ UI เปลี่ยนทันที แต่ยังไม่ใช่การบันทึกข้อมูลถาวร

## Slide 22: ข้อจำกัดก่อนต่อ Database

รายการใหม่อยู่เฉพาะใน `IssueBoard` ของหน้า Home

| จุดที่เปิด | ผลที่คาดไว้ |
|---|---|
| `/issues` | ยังอ่าน Mock Data เดิม ไม่เห็นรายการที่เพิ่งเพิ่ม |
| `/issues/new` | ตรวจข้อมูลได้ แต่แจ้งว่ายังไม่บันทึกและไม่ล้าง Form |
| รายละเอียดของรหัสใหม่ | ไม่พบรายการ เพราะยังค้นจาก `data/issue.ts` |
| Refresh หรือออกจาก Home แล้วกลับมา | State เริ่มจาก Mock Data ใหม่ |

Day 4 จะเปลี่ยนมาอ่านและบันทึก Database เพื่อให้ทุกหน้าใช้ข้อมูลเดียวกัน

## Slide 23: ตรวจฝั่ง Browser แล้ว ยังต้องตรวจฝั่ง Server

Validation ใน Browser ช่วยให้แก้ข้อมูลได้เร็ว แต่ผู้ใช้แก้ Client Code หรือส่ง Request โดยไม่ผ่าน Form ได้

ดังนั้น ก่อนบันทึกข้อมูลจริง Server ต้องตรวจข้อมูลซ้ำ แม้ Frontend จะตรวจผ่านมาแล้ว

ตอนนี้ Flow ของเราคือ: Form อ่านและตรวจข้อมูล → Callback ส่ง Issue → Board เปลี่ยน State → List แสดงผล

Hour 4 จะเพิ่มการเปลี่ยน Status ของรายการใน State ชุดเดียวกัน ก่อนเชื่อม Database ใน Day 4
