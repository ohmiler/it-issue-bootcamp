# Security, LLM-Safe Coding, and Final Demo

## Day 5 - ชั่วโมงที่ 4: มองระบบให้เป็นภาพเดียว

### เป้าหมายของชั่วโมงนี้

หลังจบชั่วโมงนี้ นักศึกษาจะสามารถ:

1. เล่าได้ว่า Request เดินทางจากหน้าเว็บไปถึง Database อย่างไร
2. อธิบายหน้าที่ของ Authentication, Authorization, Validation และ RLS ได้
3. มองหาความเสี่ยงพื้นฐานจาก Code และการตั้งค่าระบบได้
4. รู้ว่าควรเริ่มตรวจตรงไหนเมื่อระบบมีปัญหา
5. อธิบายเหตุผลของสิ่งที่สร้างมาตลอด 5 วันได้

ชั่วโมงนี้ไม่มี Feature หรือโค้ดใหม่ แต่เชื่อมสิ่งที่เรียนทั้งหมดให้เห็นเป็นระบบเดียวกัน

---

## Slide 1: จากหน้าเว็บธรรมดา สู่ระบบที่มีผู้ใช้จริง

ตลอด 5 วัน เราค่อย ๆ เพิ่มความสามารถให้ Project ทีละชั้น

| ช่วงที่เรียน | สิ่งที่ระบบทำได้ |
|---|---|
| Day 1 | วางโครงหน้าเว็บด้วย HTML และ CSS |
| Day 2 | เปลี่ยนเป็น Next.js, TypeScript และ Components |
| Day 3 | เพิ่ม Tailwind, Form และการทำงานฝั่ง Client |
| Day 4 | เชื่อม Supabase เพื่ออ่านและบันทึกข้อมูลจริง |
| Day 5 | เพิ่ม Login, Role และการควบคุมสิทธิ์ |

สิ่งสำคัญไม่ใช่แค่จำนวน Feature แต่คือเราเข้าใจมากขึ้นว่า **แต่ละส่วนควรรับผิดชอบอะไร**

---

## Slide 2: Request หนึ่งครั้งเดินทางอย่างไร

เมื่อผู้ใช้กดปุ่มบนหน้าเว็บ ข้อมูลไม่ได้เดินทางไป Database ทันที

```text
ผู้ใช้
  ↓
Page หรือ Server Action
  ↓
ตรวจ Session, Role และข้อมูลที่ส่งมา
  ↓
Supabase Client
  ↓
GRANT และ RLS
  ↓
Database
```

ถ้า Request ไม่ผ่านชั้นใด ระบบควรหยุดที่ชั้นนั้น เช่น ยังไม่ Login ให้ไปหน้า Login หรือไม่มีสิทธิ์ก็ไม่ควรแก้ข้อมูล

---

## Slide 3: Security ไม่ได้อยู่ที่จุดเดียว

แต่ละชั้นตอบคำถามคนละข้อ

| ชั้นที่ตรวจ | คำถามที่ต้องตอบ |
|---|---|
| Authentication | ผู้ใช้คนนี้คือใคร |
| Authorization | ผู้ใช้คนนี้ทำสิ่งนี้ได้หรือไม่ |
| Validation | ข้อมูลที่ส่งมาถูกต้องหรือไม่ |
| GRANT | Role นี้ใช้คำสั่งกับ Table ได้หรือไม่ |
| RLS | ผู้ใช้เข้าถึง Row ใดได้บ้าง |

เราใช้หลายชั้นเพราะไม่มีชั้นใดตอบได้ครบทุกคำถาม

Login สำเร็จไม่ได้แปลว่าทำได้ทุกอย่าง ผู้ใช้ยังต้องผ่านการตรวจสิทธิ์ของงานนั้นและข้อมูล Row นั้นด้วย

---

## Slide 4: ทำไมซ่อนปุ่มอย่างเดียวไม่พอ

การซ่อนปุ่ม Admin ช่วยให้หน้าเว็บใช้ง่าย แต่ผู้ใช้ยังสามารถพิมพ์ URL หรือสร้าง Request เองได้

```text
UI            → ไม่แสดงสิ่งที่ผู้ใช้ไม่ควรใช้
Page Guard    → กันการเปิด URL โดยตรง
Server Action → ตรวจสิทธิ์ก่อนเปลี่ยนข้อมูล
RLS           → ให้ Database ตรวจเป็นด่านสุดท้าย
```

ใน Project นี้ `canManage` ดูแล UI, `requireAdmin()` ดูแล Server และ RLS ดูแลข้อมูลจริง ทั้งสามส่วนทำหน้าที่ต่างกัน

แนวคิดนี้เรียกว่า **Defense in Depth** หรือการป้องกันหลายชั้น

---

## Slide 5: มอง Security เป็นคำถาม ไม่ใช่รายการให้ท่อง

OWASP รวบรวมความเสี่ยงที่พบบ่อยของเว็บ เราไม่จำเป็นต้องจำทุกชื่อ แต่ใช้เป็นคำถามเวลาตรวจระบบได้

| คำถาม | ตัวอย่างใน Issue Tracker |
|---|---|
| ผู้ใช้เข้าถึงเกินสิทธิ์หรือไม่ | USER เปิดหน้า Admin หรือแก้ Issue คนอื่นได้ |
| ระบบยังเปิดสิทธิ์ทดลองอยู่หรือไม่ | Demo Policy หรือสิทธิ์ `anon` ยังไม่ถูกปิด |
| Input ถูกนำไปใช้อย่างปลอดภัยหรือไม่ | นำข้อความจากผู้ใช้ไปต่อเป็น SQL โดยตรง |
| เมื่อเกิด Error ระบบเปิดเผยข้อมูลมากไปหรือไม่ | แสดง Token, Secret หรือรายละเอียดภายในบนหน้าเว็บ |

ประโยคที่ช่วยตรวจได้เสมอคือ: **ผู้ใช้ควบคุมค่าอะไรได้ และระบบตรวจค่านั้นที่ชั้นไหน**

---

## Slide 6: ข้อมูลจากผู้ใช้ต้องถูกตรวจเสมอ

ข้อมูลจาก Form หรือ URL สามารถถูกแก้ก่อนส่งมาที่ Server ได้ จึงไม่ควรเชื่อค่าจาก Browser ทันที

- ตรวจ Form ซ้ำใน Server Action
- จำกัด Status ให้เป็นค่าที่ระบบรองรับ
- ใช้ `user.id` จาก Session แทนการรับเจ้าของ Issue จาก Form
- ใช้ Supabase methods เช่น `.insert()` และ `.eq()` แทนการต่อ SQL String เอง
- แสดง Error ที่เข้าใจง่าย โดยไม่เปิดเผย Password, Token หรือ Secret

Browser validation ช่วยเรื่องประสบการณ์ใช้งาน ส่วน Server validation ช่วยรักษาความถูกต้องของระบบ

---

## Slide 7: ค่า Public กับ Secret ต่างกันอย่างไร

ชื่อ Variable ไม่ได้บอกเพียงว่าเก็บไว้ที่ไหน แต่บอกด้วยว่า Code ฝั่งใดสามารถอ่านค่านั้นได้

| ค่า | เปิดเผยใน Browser ได้หรือไม่ |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | ได้ |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | ได้ แต่ต้องใช้คู่กับ RLS |
| Password, Token และ `service_role` key | ไม่ได้ |

`.env.local` ต้องไม่ถูก Commit ส่วน `.env.example` ควรมีเฉพาะชื่อ Variable โดยไม่มีค่าจริง

Publishable key ไม่ใช่ Secret ที่ให้สิทธิ์ทุกอย่าง ความปลอดภัยของข้อมูลยังขึ้นอยู่กับ GRANT และ RLS

---

## Slide 8: ใช้ AI ช่วยได้ แต่เรายังเป็นผู้รับผิดชอบ

Code จาก AI เป็นจุดเริ่มต้นที่ดี แต่ก่อนนำมาใช้ควรถามว่า:

1. Code นี้เปลี่ยนไฟล์และ Flow ส่วนใด
2. API ตรงกับ Version ที่ Project ใช้อยู่หรือไม่
3. Input, Session และ Role ถูกตรวจที่ไหน
4. มี RLS รองรับ Operation นี้หรือไม่
5. Build ผ่านและทดสอบทั้งกรณีสำเร็จกับไม่สำเร็จแล้วหรือยัง

อย่าส่ง `.env.local`, Password, Token, Secret หรือข้อมูลส่วนบุคคลให้ AI

ถ้าเรายังอธิบาย Code ไม่ได้ ก็ควรหยุดอ่านและทดสอบก่อนนำ Code นั้นเข้า Project

---

## Slide 9: เมื่อระบบมีปัญหา ให้ไล่ตรวจทีละชั้น

ไม่ต้องรีบแก้หลายไฟล์พร้อมกัน ให้เริ่มจากอาการที่เห็น

| อาการ | จุดที่ควรเริ่มตรวจ |
|---|---|
| ปุ่มหรือข้อความแสดงไม่ถูก | Props และเงื่อนไขใน UI |
| กด Form แล้วไม่ทำงาน | Validation, Server Action และ Server Log |
| อ่านหรือเขียน Table ไม่ได้ | Supabase Error, GRANT และ RLS |
| ข้อมูลเข้าแต่หน้า List ว่าง | Session, `created_by` และ SELECT Policy |
| Local ใช้ได้แต่ Production ไม่ได้ | Environment Variables และ Deployment |

เป้าหมายของหลักสูตรไม่ใช่การจำทุก Syntax แต่คืออ่าน Flow ออก รู้ว่าควรตรวจชั้นไหน และอธิบายเหตุผลของ Code ที่เขียนได้

จากนี้สามารถต่อยอดเรื่อง Testing, Error States, Search, Pagination, Audit Log และ Monitoring ได้ตามความต้องการของระบบจริง
