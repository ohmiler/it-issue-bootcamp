# Security, LLM-Safe Coding, and Final Demo

## Day 5 - ชั่วโมงที่ 4: มองระบบให้เป็นภาพเดียว

### เป้าหมายของชั่วโมงนี้

หลังจบชั่วโมงนี้ นักศึกษาจะสามารถ:

1. เล่าได้ว่า Request เดินทางจากหน้าเว็บไปถึง Database อย่างไร
2. อธิบายหน้าที่ของ Authentication, Authorization, Validation และ RLS ได้
3. มองหาความเสี่ยงพื้นฐานจาก Code และการตั้งค่าระบบได้
4. รู้ว่าควรเริ่มตรวจตรงไหนเมื่อระบบมีปัญหา
5. อธิบายเหตุผลของสิ่งที่สร้างมาตลอด 5 วันได้

ชั่วโมงนี้ไม่มี Feature หรือโค้ดใหม่ แต่เชื่อมสิ่งที่เรียนทั้งหมดให้เห็นเป็นระบบเดียวกัน

---

## Slide 1: จากหน้าเว็บธรรมดา สู่ระบบที่มีผู้ใช้จริง

ตลอด 5 วัน Project เพิ่มความสามารถทีละชั้น:

| Day | สิ่งที่ระบบทำได้ |
|---|---|
| Day 1 | หน้าแจ้งปัญหาด้วย HTML และ CSS |
| Day 2 | ย้ายเข้า Next.js และ TypeScript แยก Component และสร้างหลายหน้า |
| Day 3 | ตกแต่งด้วย Tailwind แล้วเพิ่มและเปลี่ยนสถานะรายการใน State |
| Day 4 | อ่าน เพิ่ม และเปลี่ยนสถานะใน Supabase แล้ว Deploy |
| Day 5 | Login และแบ่งสิทธิ์ USER กับ ADMIN |

**ชั่วโมงนี้:** ไม่มีโค้ดใหม่ แต่ทบทวนว่าแต่ละส่วนของระบบรับผิดชอบอะไร และตรวจความเสี่ยงพื้นฐาน

## Slide 2: Request หนึ่งครั้งเดินทางอย่างไร

ตัวอย่าง: ADMIN กดปุ่ม `DONE` ในหน้า `/admin/issues`

```text
กดปุ่ม → ฟอร์มส่ง id และ status ไปที่ Server
  ↓
updateIssueStatusAction: requireAdmin() ตรวจ Login และ Role
                         allowedStatuses ตรวจว่าสถานะถูกต้อง
  ↓
updateIssueStatus: ส่งคำสั่งแก้ข้อมูลผ่าน Supabase Client
  ↓
Database: ตรวจ grant และ Policy ของ RLS ซ้ำ แล้วจึงแก้แถวใน issues
```

ถ้าไม่ผ่านขั้นไหน ระบบจะหยุดตรงนั้นก่อนถึง Database เช่น ยังไม่ Login จะถูกพาไป `/login` และ USER จะถูกพากลับ `/issues`

---

## Slide 3: แต่ละชั้นตรวจอะไร

| ชั้น | ตอบคำถาม | ในโค้ดของ Project |
|---|---|---|
| Authentication | ผู้ใช้คือใคร | `requireUser()` อ่าน Session |
| Authorization | ผู้ใช้ทำสิ่งนี้ได้ไหม | `requireAdmin()` ตรวจ Role ใน `profiles` |
| Validation | ข้อมูลที่ส่งมาถูกต้องไหม | `validateIssueInput` และ `allowedStatuses` |
| `grant` | กลุ่มผู้ใช้นี้ใช้คำสั่งนี้กับ Table ได้ไหม | `grant select, insert, update ... to authenticated` |
| RLS | ผู้ใช้คนนี้อ่านหรือแก้แถวไหนได้ | Policy `users_view_own_admins_view_all` |

กลุ่มผู้ใช้ของ `grant` คือ `anon` (ยังไม่ Login) และ `authenticated` (Login แล้ว) ต่างจาก Role `USER` กับ `ADMIN` ที่ระบบนี้เก็บใน `profiles`

Login สำเร็จไม่ได้แปลว่าทำได้ทุกอย่าง คำขอต้องผ่านทุกชั้นที่เกี่ยวข้อง

---

## Slide 4: ทำไมซ่อนปุ่มอย่างเดียวไม่พอ

USER มองไม่เห็นปุ่มเปลี่ยนสถานะ แต่ยังพิมพ์ URL เองหรือส่งฟอร์มเลียนแบบได้ ระบบนี้จึงกันหลายชั้น:

| จุดที่กัน | ผล |
|---|---|
| `canManage` | ซ่อนปุ่มจาก USER ช่วยให้ใช้ง่าย แต่ไม่ได้กันจริง |
| `requireAdmin()` ในหน้า `/admin/issues` | USER พิมพ์ URL เองก็ถูกพากลับ `/issues` |
| `requireAdmin()` ใน Server Action | USER ส่งฟอร์มเองก็ถูกหยุดก่อนแก้ข้อมูล |
| Policy ของ RLS | ถ้าโค้ดฝั่ง Server พลาด Database ก็ยังไม่ยอมให้แก้ |

การป้องกันหลายชั้นแบบนี้เรียกว่า **Defense in Depth** ถ้าชั้นหนึ่งพลาด ชั้นถัดไปยังกันไว้

## Slide 5: ตรวจความเสี่ยงด้วยคำถาม

**OWASP** คือกลุ่มที่รวบรวมความเสี่ยงที่พบบ่อยของเว็บ ไม่ต้องจำชื่อทั้งหมด ให้ใช้เป็นคำถามตรวจระบบ:

| คำถาม | ตัวอย่างความเสี่ยง | ระบบนี้กันด้วย |
|---|---|---|
| ผู้ใช้ทำเกินสิทธิ์ได้ไหม | USER แก้สถานะ Issue | `requireAdmin()` และ RLS |
| ยังเปิดสิทธิ์ทดลองค้างไว้ไหม | Policy `demo_` ยังอยู่ | ลบ Policy `demo_` และถอนสิทธิ์ของ `anon` แล้ว |
| เชื่อค่าจาก Browser ไหม | แก้ `status` หรือเจ้าของ Issue ในฟอร์มเอง | `allowedStatuses` และใช้ `user.id` จาก Session |
| เอาข้อความผู้ใช้ไปต่อเป็นคำสั่ง SQL ไหม | ข้อความในฟอร์มกลายเป็นคำสั่งลบข้อมูล | `.insert()` และ `.eq()` ของ Supabase แยกค่าออกจากคำสั่ง |

ประโยคที่ใช้ตรวจได้เสมอ: **ผู้ใช้ควบคุมค่าอะไรได้ และระบบตรวจค่านั้นที่ชั้นไหน**

## Slide 6: ค่า Public กับ Secret ต่างกันอย่างไร

ค่าที่ขึ้นต้นด้วย `NEXT_PUBLIC_` ถูกส่งไปถึง Browser ใครเปิดเว็บก็ดูได้ จึงใส่ได้เฉพาะค่าที่เปิดเผยได้

| ค่า | เปิดเผยได้ไหม | เหตุผล |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | ได้ | เป็นแค่ที่อยู่ของ Project |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | ได้ | ทำได้แค่ที่ `grant` และ RLS อนุญาต |
| Secret Key, `service_role` Key และ Database Password | ไม่ได้ | ข้าม RLS หรือเข้า Database ได้ทั้งหมด |

`.env.local` ห้าม Commit ส่วน `.env.example` มีแค่ชื่อค่า และข้อความ Error บนหน้าเว็บต้องไม่มี Token หรือ Secret

## Slide 7: ใช้ AI ช่วยได้ แต่ผู้เขียนยังต้องรับผิดชอบ

โค้ดจาก AI เป็นจุดเริ่มต้นที่ดี แต่ก่อนนำมาใช้ให้ถามว่า:

1. โค้ดนี้เปลี่ยนไฟล์และ Flow ส่วนไหน
2. ใช้คำสั่งตรงกับ Version ของ Project ไหม เช่น Next.js 16 ใช้ `proxy.ts` ไม่ใช่ `middleware.ts`
3. ตรวจ Login, Role และข้อมูลที่ส่งมาที่ไหน
4. มี `grant` และ Policy รองรับคำสั่งนี้ไหม
5. `npm run build` ผ่าน และทดสอบทั้งกรณีสำเร็จและไม่สำเร็จแล้วหรือยัง

อย่าส่ง `.env.local`, Password, Token, Secret หรือข้อมูลส่วนบุคคลให้ AI และถ้ายังอธิบายโค้ดไม่ได้ ให้หยุดอ่านและทดสอบก่อนนำเข้า Project

## Slide 8: เมื่อระบบมีปัญหา ให้ไล่ตรวจทีละชั้น

เริ่มจากอาการที่เห็น แล้วตรวจทีละจุด ไม่ต้องแก้หลายไฟล์พร้อมกัน

| อาการ | เริ่มตรวจที่ |
|---|---|
| ปุ่มหรือข้อความแสดงไม่ถูก | Props และเงื่อนไขใน Component เช่น `canManage` |
| กดส่งฟอร์มแล้วไม่ทำงาน | Server Action และ Error ใน Terminal ที่รัน `npm run dev` |
| ขึ้น `permission denied` หรือ `row-level security` | `grant` และ Policy ใน Supabase |
| เพิ่มข้อมูลได้แต่หน้ารายการไม่แสดง | Login อยู่ไหม, `created_by` ถูกบันทึกไหม และ Policy ของ `select` |
| ขึ้น `fetch failed` ทุกหน้า | Supabase Project ถูกพักไว้ไหม ถ้าใช่ให้กด Restore ใน Dashboard |
| เครื่องตัวเองใช้ได้แต่ Production ไม่ได้ | Environment Variables และ Logs ใน Vercel |

เป้าหมายของหลักสูตรไม่ใช่การจำทุกคำสั่ง แต่คืออ่าน Flow ออก รู้ว่าควรตรวจชั้นไหน และอธิบายเหตุผลของโค้ดที่เขียนได้
